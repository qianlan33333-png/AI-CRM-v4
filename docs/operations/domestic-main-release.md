# CRM v4 日常国内发布

**默认采用已实测的热修同包路径。** 一个开发任务交付准确候选，同一发布者从检查推进到生产读回和源码对齐。GitHub 由用户人工择机归档，不是部署前置。预备机 `10.0.4.6` 保持 2 核 2GB，生产机 `10.0.4.13`；源码和生产包都留在国内。

## 日常路径

1. **交付候选。** 独立 `codex/*` 分支/worktree 提供准确 base/head/tree、简短影响说明、相关测试结果与未验证项。基于当前国内源码主线；过期或冲突由原开发任务更新重验。候选可含同一完整行为的多个提交，不按行数拆分，不需要 GitHub PR、merge-preview 或 handoff ACK。
2. **相关检查与构建一次。** 发布者持现有串行锁核对整个 base→head 区间。运行受影响包全集及相关合成旅程；相同代码树、基线、检查范围和工具环境的准确 Linux 证据可复用，macOS 证据不代替必需 Linux 验证。未知、共享基础、迁移或检查策略变化按实际影响扩大。预备机复用已有构建缓存和已验证文件，生成完整清单；不另开全量治理任务。
3. **预发安装，再同包生产。** 安装准确包，检查受影响页面/接口、服务与健康；支付等外部效果用虚拟 Provider，不能只看登录页。通过后自动保存并验证完整源码 Git bundle，再以内网传变化文件，晋级这份包，生产不重新编译或打包。
4. **读回并收尾。** 独立核对生产 SHA、完整文件摘要、服务进程、`/readyz` 和本次适用的安全业务读回；成功后由同一任务完成国内 `main` 的 CAS、源码游标和既有发布收据对齐。真实付款/扫码另行验收，不填截止日期、不占下一次技术发布通道，不冒称已完成业务验收。

单次入口复用现有控制器，参数为准确分支和源码身份：

```sh
sudo /usr/local/libexec/aicrm/domestic_main_release.py release --config /etc/aicrm/domestic-main-release.json --ref refs/heads/codex/<work-item> --head <SHA> --base <SHA>
```

该入口是已有 `submit` + `poll` 的一次调用，保留队列顺序与锁；已有更早候选时不能冒称本候选已发布。工具尚未安装该入口的节点继续由同一负责人调用现有函数完成同样流程，不能凭修改说明启动定时器或假定自动发布已生效。

## 哪些情况加步骤

| 实际变化 | 增加的必要验证 |
| --- | --- |
| 普通页面/程序 | 相关测试、预发旅程、生产读回；不备份或迁移数据库 |
| 数据库迁移 | 完整迁移与兼容检查，只有生产机迁移前备份；预备机使用可重建合成数据 |
| 发布工具/主机行为 | 对应控制器、安装器、恢复合同及必要真实主机演练；与业务候选分开维护 |
| 文档/skill | 本地格式、引用和规则检查后生效；不构建、不安装应用、不等待 GitHub |

## 停止与恢复

源码、基线、包摘要、必要测试或预发合同不符就停止该候选，不能省检查来掩盖失败。生产失败按现有安装器回滚并读回；安装结果不明时停队列，只读核对原 attempt/current/receipt/源码 bundle/健康，已安装成功则仅收尾对齐，绝不重新安装。始终一个生产写者，旧发布入口不得同时运行。凭据、生产配置和收据继续保留既有权限，源码快照权限按用途处理。

## GitHub 与当前切换状态

GitHub 凭据只留在用户电脑，无自动推送、无定期同步、未同步不阻塞发布。人工执行 `scripts/manual_github_sync.py` 时先预览；只有国内 `main` 和生产源码收据一致，GitHub 是其祖先时才显式 `--execute` 普通快进，拒绝分叉和强推。

2026-09-26 两项热修已安装为 `47218821`，全部 542 文件摘要和服务/健康读回通过；此次直发后的国内 main、账本和生产源码游标已依据真实安装收据 CAS 对齐同一准确版本，未重新安装；新旧 timer 保持关闭。这个对账已经收尾，不是每次业务发布重新跑初始化。完整故障恢复和历史初始化见 `domestic-main-bootstrap.md`，仅在对应问题发生时使用。最新源码 bundle 保存在生产 `/opt/aicrm/domestic/source-backups/`；两台国内机器在人工归档前同时丢失时，GitHub 可能缺少未同步代码。
