1. 先完成旧生产 receipt/当前 `/readyz` 只读核对，并保存带 `observed_at`（UTC、十分钟内）、`release_sha`、`tree_sha`、`package_sha256`、`readyz.release_sha` 和 `readyz.status` 的 JSON 读回。保留它的 SHA-256，不把旧真实业务项记为通过。
2. 完成最终批次 handoff。由独立聚合任务把源 PR #15/#3/#13 和治理 PR #19 的准确 heads 以有审计的普通 Git merge 汇成一个新聚合 PR；#17 若为预发分槽所需，只能作为独立治理祖先或先进入 main，不列作 runtime 成员。PR #19 在当前旧 main 单独 full CI 受 #15 基线阻断，不先合并或冒称全绿；它只作为已审治理来源进入组合树。聚合 PR 是唯一进入 GitHub protected main 的合并单元，必须在当前 head 上通过 required `check` 和显式完整 CI，源 PR 的单独红灯不能冒充绿灯。`first_v4_batch_bridge` 字段指向桥 JSON。`members` 精确保存 #15/#3/#13 各自 `work_item`、commit/tree/receipt，PR #19/#17 不列为运行时业务成员；批次 handoff 必须按现有批次校验器证明每个成员属于联合 preview，accepted package/receipt 与各自受影响旅程成立。
3. 桥 JSON 固定 `schema: 1`、`exception_id: first-v4-joint-batch-v1`、`repository: qianlan33333-png/AI-CRM-v4`。`legacy` 写旧 candidate/release/tree/package 和旧 production receipt 的绝对路径与 SHA-256；`v4_root` 写根 commit/tree；`batch_manifest_sha256` 写整个 handoff 的字节摘要。`batch` 写 candidate ID、base main、aggregate head、merge preview、candidate tree、package SHA-256、accepted receipt SHA-256；`aggregate_pr` 写聚合 PR URL、head SHA、tree SHA；`governance_pr` 写 PR #19 URL、最终 head SHA/tree SHA，且该 commit 必须是 aggregate head 的祖先；`full_ci_run_id` 写聚合 head 的完整 CI run ID。`members` 按 handoff 顺序写各源 PR 的 `pr_url`、`commit_sha`、`tree_sha`。`production_readback` 写步骤 1 的绝对路径与摘要。
4. 用户在指挥台原始消息中已要求完成两项部署，`user_authorization` 记录该消息的 `user_thread_id`、`user_message_id`、`decision_text` 和字节摘要证据（证据 JSON 同字段，`source: user_message`）。`queue_authorization` 与 `production_authorization` 是指挥台对冻结后精确候选的两条 operator attestation，不要求用户再次回答。每项包含 `decision: approved`、唯一 `decision_id`、`recorded_by_thread_id`、`authority_message_id`（等于上述用户消息）、`decision_text`、`candidate_id`、`merge_preview_sha`、`package_sha256`、UTC `expires_at` 和 `evidence`。证据 JSON 含相同字段和 `source: operator_attestation`，由绝对路径与 SHA-256 引用。两条 operator 记录须在一次性入队前冻结于同一桥文件；入队后修改桥文件会破坏消费摘要并使晋级失败。
5. 校验与入队：先核对聚合 head 的签名 source bundle、完整 CI、required check、预发 accepted package 和 `git rev-parse HEAD`；仅从这个准确 checkout 的已审桥脚本运行 `python3 scripts/release_first_v4_batch_bridge.py validate --bridge BRIDGE.json --batch HANDOFF.json --queue QUEUE.json`。候选已由指挥台凭 accepted receipt 验收、处于 `staging_acceptance` 或 `frozen` 后，执行 `admit`（同参数）。它在队列锁下将旧候选写入不可改绑的 candidate/桥摘要消费标记，再把新候选移至 `waiting_merge`。不使用本地未审脚本手工修改 state，不重复执行 `admit`。旧观察不变。
6. 指挥台串行合并、核对合并后 main tree 与 accepted candidate tree。指挥台从 GitHub 重新读取准确合并后 main，按现有 `release_freshness.py issue --stage promotion` 签发短时证明，绑定 aggregate head/tree、preview/tree、原 source bundle 和同一 accepted package；预发节点持固定 allowed-signers 公钥并离线验签、核 bundle/package 摘要。晋级前重新保存十分钟内的独立生产读回 JSON；它可以晚于冻结桥文件，但必须包含与步骤 1 相同的全部字段。使用既有 `release_control.py release promote --prepare/--execute`，两阶段都加 `--bridge-readback FRESH-READBACK.json --bridge-attestation PROMOTION.json --bridge-signature PROMOTION.sig --bridge-allowed-signers ALLOWED_SIGNERS --bridge-bundle CANDIDATE.bundle`；它在精确批次上重验已消费桥摘要、成员 Git commit/tree、旧生产读回、同包和队列标记。GitHub 在线 PR/check/全 CI 状态仅在 `admit` 时核对并由不可改绑的桥摘要冻结；晋级使用短时已签名的 main 新鲜度证明，不让预发机重复请求 GitHub。执行阶段还用 SSH 实时 `/readyz` 与这份读回比对。晋级器仍只在可信预发 Linux 节点运行，使用原有锁、固定 Host Key 和同一包；网络尝试前保留 attempt。结果不明只读对账，不重新发包。

任一 PR head、main、receipt、package 或读回变化，桥记录立即失效；重建候选、证据并重新取得相应决定。合并保护和 required checks 不变。桥消费后不能用于下一包。技术 `observing`、发送 ack、虚拟预发效果和用户口头陈述不能代替支付宝实付、企微入群码及旧三项真实业务验收。
