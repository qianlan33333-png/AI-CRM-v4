# CRM v4：国内主仓与人工 GitHub 归档

日期：2026-09-25。父需求已由用户批准。本文件只定义源码权威、发布和归档边界，不改变业务 API 或数据库模型。

## 业务判断与流程

唯一开发者可以同时开多条 Codex 开发线。每条线使用独立 worktree 和 `codex/<work-item>` 分支，只把分支推到预备机的裸仓库；只有一个发布器可以推进国内 `main`。每个候选基于提交时的国内 `main`，过期候选由原开发线更新并重新验证。后一个生产版本包含已上线的前一个版本，不支持从新版本抽掉某个已上线板块。

```mermaid
flowchart LR
  A[独立工作树和分支] --> B[推送国内分支]
  B --> C[准确基线与影响检查]
  C --> D[预备机构建、安装、合成验收]
  D --> E[完整 Git bundle 传生产并验真]
  E --> F[同一安装包内网晋级]
  F --> G[生产版本、摘要、服务、健康读回]
  G --> H[CAS 推进国内 main]
  H -. 人工择机 .-> I[GitHub 快进归档]
```

成功的技术发布须有准确源码 SHA/tree、相同安装包摘要、生产源码备份摘要、生产安装收据和健康读回。真实支付等业务验收另记，不由合成测试或健康读回代替。纯文档提交不装应用，但仍在生产保存可恢复源码并推进已处理源码游标。

## 参考与仓库复用

- Git 的 [worktree](https://git-scm.com/docs/git-worktree) 允许同一个仓库保留独立工作目录；[bundle](https://git-scm.com/docs/git-bundle) 可离线保存对象及引用，并可验证对象完整性和前置对象；[push](https://git-scm.com/docs/git-push) 的普通快进规则用于手工 GitHub 归档。
- [Git 接收钩子](https://git-scm.com/docs/githooks)可拒绝开发者直接更新裸仓库 `main`；发布器还必须在锁内用 `update-ref <new> <old>` 做最终比较并交换，不能只依赖钩子。
- 复用本仓 `scripts/domestic_release_build.py` 的增量构建、`deploy/domestic-promote.py` 的主机角色、迁移备份、不可变安装、摘要和健康读回，以及 `scripts/dev_preflight.py` 的影响检查。旧 GitHub API 检查、main 轮询和 GitHub `main` 作为生产权威的逻辑在切换后退出日常路径。

## 数据与权限边界

- OneID：不涉及；发布器不读写客户身份。
- Persistence：本地持久队列、锁、准确 SHA/tree、阶段收据和生产源码备份。业务数据库由现有领域持有；预备机只用合成测试数据。
- External Effects：部署会切换生产服务，是需幂等对账的运维效果；不新增支付、退款或企微 Provider 效果。生产安装结果不明时只读对账，不重新安装。
- 预备机裸仓库仅接受开发者分支更新；开发者没有直接写 `main`、生产部署凭据或共享预发目录的权限。执行候选测试的构建账号对权威 Git 对象库只读，与可写分支的推送账号分离。发布器独占 `main` 更新和生产晋级。GitHub 凭据只在用户电脑。
- 普通发布不备份数据库。生产迁移依旧在安装前做现有整库备份；预备机迁移使用可重建的合成数据库，不备份生产数据到预备机。

## 失败与恢复合同

1. 候选 base 不等于当前国内 `main`、SHA/tree 不匹配、影响检查缺失或失败：拒绝候选；发布器不 rebase、不解决冲突。
2. 预备机构建或已安装业务合同失败：停止在该候选，不更新国内 `main`，不触碰生产。
3. 生产端须在安装前收到自包含、可由空仓库恢复的准确提交 Git bundle；验证 bundle、SHA/tree 和摘要后才允许安装。源码备份不自动清理；容量不足时停队列，人工确认最新 bundle 和 GitHub 归档范围后才处理旧备份。
4. 生产安装明确失败：沿用现有回滚并验证旧版健康；结果不明：停止队列，只读比较 current、收据、文件摘要、服务与 bundle。若已健康安装但国内 `main` 尚未更新，仅允许准确收据对账后 CAS 完成推进，禁止再安装。
5. 仅在国内 `main` 等于生产已安装源码、GitHub `main` 为其祖先时，人工同步命令才允许普通快进推送。显示待同步数；远端前进、分叉或推送后读回不符均停止，绝不强推。没有定时器、自动推送或同步周期。
6. 预备机丢失时，从生产机最新已验证 bundle 和收据恢复裸仓库，再重建工作树。两台国内机器在 GitHub 归档前同时丢失，则未归档代码可能不可恢复；产品明确接受这一代价。

## 切换顺序与验收

先按当前流程完成 PR #39，核对 GitHub、预备机、生产当前 SHA/tree/manifest；确认旧定时器及其已触发的 service 都已退出。随后在预备机实测 2 核、2GB 的检查和构建，演练双分支串行、过期基线、预发失败、生产健康失败、安装结果不明、生产 bundle 恢复、人工快进与远端分叉。通过后才启用国内发布入口，并把 GitHub `main` 改成保留禁止强推与删除的归档保护；GitHub Actions 不再决定生产发布。切换完成后撤销旧预备机只读 GitHub deploy key 并清除其私钥，保留独立的生产内网部署凭据。

未完成切换时，GitHub 仍是发布权威。未通过资源实测时先扩容或维持旧流程，不能减少必要检查来宣称提速。
