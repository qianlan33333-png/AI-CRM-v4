# CRM v4 日常发布精简

## 判断与范围

用户已明确：刚才两项热修采用的路径就是日常发布路径；GitHub 人工择机归档，预备机维持 2 核 2GB。统一本地开发入口并复用现有国内发布函数，不建设第二发布器，不改业务 API、数据库、Provider 配置或生产应用。

当前本地 `AI-CRM-v4` 主目录的 skill 仍要求 GitHub merge-preview、四级 handoff、短时 freshness 和观察占位；已上线候选则使用国内源码、受影响测试、构建一次和同包晋级。先消除规则冲突，再仅修复现有执行器的具体阻塞。既有热修的业务测试不能因更改流程而冒称全量回归。

```mermaid
flowchart LR
 A[开发提交准确候选与相关测试] --> B[同一发布者核对基线和影响]
 B --> C[国内相关测试与构建一次]
 C --> D[预发安装及相关合成旅程]
 D --> E[源码 bundle 保存与内网同包晋级]
 E --> F[生产版本 文件 服务 健康读回]
 F --> G[自动完成源码 main 与收据对齐]

```

## 参考与复用

- [Deployment Pipeline](https://martinfowler.com/bliki/DeploymentPipeline.html)：构建产物在后续阶段复用，依据真实瓶颈精简流水线。
- [Trunk Based Development](https://trunkbaseddevelopment.com/)：短分支与一条累计主线。这里只采用短分支和单一主线，不采用其 GitHub、cherry-pick 或其他与用户选择冲突的机制。
- 仓库直接复用 `domestic_main_release.py` 的检查、构建、源码备份、串行锁和 CAS，以及 `domestic_release.py`、`domestic-promote.py` 的安装/读回/回滚。开发核心 skill 的限制必要性规则保持完整。

OneID：不涉及；不改变客户身份。Persistence：复用既有发布收据和队列，不新增业务表或第二状态机。External Effects：仅既有部署操作，不发起支付、退款或企微写入。本次没有 UI 开发。

## 保留与删除

保留准确 SHA/tree、单一生产写者、影响范围测试、同一包、生产读回、结果不明只读对账。它们分别防止源码错版、并行覆盖、回归、二次构建漂移和重复安装。

撤下日常 GitHub PR/check/merge-preview/freshness、handoff ACK、重复父 PRD/独立任务、真实验收截止日期、观察占用技术通道。完整初始化与工具维护仅在相应变更或故障时执行。普通页面/程序不备份或迁移；只有生产数据库迁移才备份。文档/skill 本地生效，无应用安装。

## 检查与执行

按实际影响选择包全集和相关旅程，不能按行数或新旧代码判断风险。准确 Linux 证据已有且代码、测试、工具链、基线与计划仍匹配时复用；仅 macOS 通过不能省掉必需 Linux 验证。共享、迁移、检查策略或未知影响仍执行相应扩大检查。

测试、构建、安装后 smoke 均覆盖整个候选区间，不仅最后一个提交。预发只有合成数据和虚拟 Provider。候选基线过期由原开发者更新重验，发布者不解决源码冲突。生产读回成功后源码对齐是同一任务收尾，不能像本次直发一样长期留下账本落后。

## 验证与交付

检查三个场景：文档变更无应用构建；局部页面不加备份/迁移/真实支付前置；多提交支付候选覆盖整个区间的安装后合同。若修改执行器，则跑对应发布器合同，不重复无关应用全量测试。所有本地入口读到同一规则；不自动推 GitHub，不重新安装已经上线的 47218821，也不恢复尚未验证的 timer。
